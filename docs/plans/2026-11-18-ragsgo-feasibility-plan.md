## 0. 요약

- **연산량만 보면 실시간 처리는 가능하다** [추정]. 신경망을 빼고 계산하면 휴대폰 CPU 한 코어의 1~수 % 수준이다. 측정한 값은 아니다.
- **정확도는 확인되지 않았다.** 드럼이 있는 밴드 전체 소리에서 동작한다고 밝힌 연구나 제품은 찾지 못했다. 이 프로젝트의 핵심 위험이다.
- **Phase 1-a 첫 진단 (2026-11-18)**: 띵바츄 1곡에서 실시간 방식 정렬이 오프라인 경로와 반 마디 안 90%, 반 박 안 58%로 맞았다 [진단, 정답 아님]. Phase 1-b에서 기준 경로 자체가 일부 구간에서 1~4박 틀린 것을 찾아, 임시 정답으로 다시 재니 반 마디 안 94%, 반 박 안 79%였다. 1:03 결과는 원곡이 다른 곡이어서 생긴 것이다(1-b). 결과 문서: `docs/results/2026-11-18-phase1a-results.md`
- **Phase 1-b (2026-11-18)**: 박 추적(인과 HMM) + 박 단위 정렬 + 넘김 예측 절차를 띵바츄에 돌렸다 (임시 정답, 사람 확인 전). 곡을 처음부터 치면 박 번호 100%, 실제 넘김 5/5, 모든 마디선 95/95가 ±1박 안이었다 (최대 0.24박). 휴대폰 대역·자동 음량 조절·템포 ±5% 흉내에서도 같았다. 멈췄다 다시 치는 경우는 자동으로 찾기 어려워 구간 탭이 필요해 보인다. 한 곡뿐이라 판정은 보류. 결과 문서: `docs/results/2026-11-18-phase1b-results.md`
- **성공 가능성은 현재 결정 그대로 20~30%로 본다** [추정, 14장]. 대부분은 아직 측정하지 않아서 생긴 불확실성이다. 앱을 만들기 전에 보유 데이터로 핵심 위험을 먼저 재는 것이 가장 효과가 크다 [제안].
- **넘김 방식은 페이지 전체 넘김이고, 페이지 끝에 딱 맞게 넘긴다** [확정, U10·U11]. 일찍 넘김은 1박까지만 허용하므로 허용 오차는 ±1박, 시범곡 기준 ±0.71초다(2.2절).
  - 반 페이지 넘김이었다면 허용 오차가 약 10마디였다. v1의 "페이지 단위 정확도면 충분하다"는 그 경우에만 성립한다.
  - 이 요구를 맞추기 위해 구조를 2단으로 바꾸는 것을 제안한다 [제안, 4.7절]. 정렬로 "몇 번째 박인지"를 파악하고, 박 추적으로 정확한 타이밍을 잡는다. 드럼 소리는 정렬에는 방해가 되지만 박 추적에는 가장 분명한 신호다.
- **넘김은 반응이 아니라 예측으로 한다** [확정 방향, U12]. 듣고 나서 반응하면 항상 늦고, 특히 정렬 결과는 0.4~0.7초 늦게 나온다 [추정]. 넘김 2마디 전에 박 번호를 확인하고 넘길 시각을 예약한 뒤, 박이 들릴 때마다 고친다 [제안, 4.7절].
  - 박 번호가 맞으면 타이밍 오차는 ±0.3박 안으로 본다 [추정]. 그래서 정확도 문제는 "넘김 지점 부근에서 박을 하나도 잘못 세지 않는 것"으로 모인다.
- **듣는 기기는 각 멤버의 모바일 기기이고, 내장 마이크로 듣는다** [확정, U13]. 믹서 출력이나 외장 마이크 같은 별도 장비는 전제하지 않는다. 기본 구조는 기기마다 각자 듣고 각자 넘기는 것으로 정리했다 [제안, D2].
- **기준 음원은 원곡이다** [확정, U14]. 새 곡도 첫 합주부터 자동 넘김이 돼야 한다. 그래서 핵심 문제는 "내장 마이크로 들은 드럼 큰 합주 소리"를 "스튜디오 원곡"에 박 단위로 맞추는 것이다. 원곡 쪽은 미리 한 번만 처리하면 되므로 신경망 음원분리 같은 무거운 처리를 쓸 수 있다 [제안, 4.8절].
- **원곡을 넣는 방법은 두 가지로 제안한다** [제안, 4.9절]. 원곡을 아무 앱으로 틀어 두고 앱이 마이크로 듣는 방법과, 음원 파일을 넣는 방법이다. 마이크로 들으면 파일이 필요 없고, 듣는 동안 넘김 지점을 탭해서 곡 준비가 한 번에 끝난다. 저작권 부담을 줄이도록 원곡 소리는 저장하거나 공유하지 않고 분석 결과만 남긴다 (사용자 지적, U15).
- **소리를 듣고 넘기는 기술 자체는 이미 상용 앱에 있다.** CueFlip과 Score Flip은 녹음을 기준으로 연주 위치를 실시간 추적한다. 이 프로젝트에 남는 차별점은 두 가지이고, 둘 다 제공하는 제품은 확인되지 않았다.
  1. 드럼을 포함한 밴드 전체 소리에서 동작한다. v3.3: 원곡만을 기준으로 첫 합주부터 동작한다는 점(U14)도 CueFlip과 다르다. CueFlip은 공식 사이트 설명상 직접 한 번 연주한 녹음을 기준으로 쓴다.
  2. 한 기기가 들은 위치를 멤버 각자의 파트 악보에 공유한다. v3.2에서 기본 구조를 "기기마다 각자 듣기"로 정리해서 이것은 나중에 붙일 선택 기능이 됐다. 기본 구조만 보면 CueFlip·Score Flip과 같으므로, 지금 남는 핵심 차별점은 1번이다.
- 그래서 직접 만들기 전에 기존 앱을 합주실에서 시험하는 단계를 제안한다 [제안]. 드럼 환경에서 정확도가 나오는지를 적은 비용으로 먼저 확인할 수 있다.

## 2. 실시간 처리 가능성

### 2.1 연산량 [추정]

계산 조건은 다음과 같다.
- 22.05 kHz 모노로 받는다.
- STFT와 HPSS는 짧은 hop(512 샘플, 약 23 ms, 초당 43 프레임)에서 처리하고, 크로마는 초당 10 프레임으로 묶는다.
- 시범곡 길이는 281초다. 크로마로 약 2,800 프레임이다.

| 단계 | 초당 연산 횟수 | 비고 |
|---|---|---|
| STFT (창 4096, 초당 43회) | 약 700만 | FFT 1회에 약 15만 회 |
| 인과적 HPSS (시간축·주파수축 중앙값 필터) | 약 1,500만 | 주파수 bin 2,049개마다 중앙값 계산 |
| 크로마 (12차원) | 10만 미만 | |
| OLTW (탐색 폭 300 프레임 = 기준 녹음 30초) | 약 8만 | 프레임당 300칸 |
| 전역 재탐색 (최근 8초를 곡 전체와 비교, 1초에 1번) | 약 600만 | 80 × 2,800칸 |
| 합계 | 약 3,000만 | |

- 최근 휴대폰 CPU 한 코어는 초당 수십억 회 연산을 처리한다. C/C++로 구현한다는 전제에서 1~수 % 수준이다.
- **이 표에 들어 있지 않은 것**이 두 가지 있다. BeatNet 같은 신경망 박 추적과, 신경망 음원분리다. 둘 다 연산량이 훨씬 크고 측정하기 전에는 알 수 없다. 쓸지 말지는 Phase 1 결과를 보고 정한다. 단, 원곡 쪽 음원분리는 곡을 추가할 때 한 번만 하므로 실시간 연산량과는 상관없다 (U14, 4.8절). 기기에서 한 번 돌리는 데 걸리는 시간은 확인해야 한다.
- 노트북의 Python 프로토타입(numpy 벡터 연산)에서도 실시간 처리에는 문제가 없을 것으로 본다.

### 2.2 넘김 타이밍과 허용 오차

v1은 넘김 허용 구간을 "마지막 마디 직전 마디의 시작 ~ 마지막 마디의 끝"으로 정의했다. 이 정의는 틀렸다. 페이지 전체를 넘기면 넘기는 순간 그 두 마디가 화면에서 사라진다.

넘김 방식별로 다시 계산한다. 기준은 시범곡 Think About'chu다.
- ♩=85이므로 1박은 0.71초, 1마디는 2.82초다.
- 악보 2페이지는 15~34마디로 20마디이고, 연주 시간은 약 56초다.

| 방식 | 언제 넘기나 | 허용 오차 | 시범곡 기준 |
|---|---|---|---|
| 전체 넘김 | 페이지 끝에 맞춰 (U11) | 일찍 넘기는 쪽: 연주자가 마지막 부분을 외워서 칠 수 있는 만큼. 늦게 넘기는 쪽: 다음 페이지 첫 박 전까지 | U11로 "일찍 최대 1박"을 정했다. 늦게 최대 1박(가정)과 합쳐 전체 2박, 약 1.41초다 |
| 반 페이지 넘김 | 1단계: 연주자가 아래쪽 절반으로 내려가면 위쪽 절반을 다음 페이지의 위쪽으로 바꾼다. 2단계: 연주자가 그 위쪽으로 올라가면 아래쪽 절반도 바꾼다 | 각 단계마다 해당 절반을 연주하는 시간 전체 | 약 10마디, 약 28초 |
| 가로 두 페이지 [제안, 동작 방식 미정] | 연주자가 오른쪽 페이지로 넘어가면 왼쪽 페이지를 그다음 페이지로 바꾼다 | 한 페이지를 연주하는 시간 전체 | 약 20마디, 약 56초. 대신 화면이 작아 글자가 작다 |

- **전체 넘김**은 여유가 앞뒤로 1박(0.71초)씩뿐이다(U11). 이는 정렬 처리 지연(2.3절, 0.4~0.7초)과 비슷하다. 그래서 미래 위치를 예측해서 미리 넘겨야 하고(U12), 박 번호도 틀리면 안 된다. 박 단위 정확도가 필요하다.
- **반 페이지 넘김**은 허용 오차가 수 마디로 늘어난다. 정확도 요구를 가장 크게 낮추는 선택이다. 다만 화면 가운데에 페이지 경계가 생기므로 멤버가 이 표시 방식에 익숙해져야 한다. forScore에도 같은 기능이 있다. forScore에서는 세로 모드에서만 쓸 수 있고, 사람이 두 번 탭해서 넘긴다.
- 일찍 허용량은 1박으로 정했다(U11). 늦게 허용량 1박은 아직 가정이다 (10장 8번).

#### 전체 넘김으로 정한 뒤의 요구 정확도 (v3)

넘김 허용 범위는 [페이지 끝 − 일찍 허용량, 페이지 끝 + 늦게 허용량]이다. 늦게 허용량은 1박으로 가정한다. 목표 시각을 이 범위의 가운데에 두면, 범위 길이의 절반이 허용 오차가 된다.

| 일찍 허용량 (D7) | 허용 범위 길이 | 목표 시각 | 허용 오차 | 시범곡(♩=85) 기준 |
|---|---|---|---|---|
| 1마디 (마지막 마디 시작부터) | 5박 | 페이지 끝 1.5박 전 | ±2.5박 | ±1.76초 |
| 2박 | 3박 | 페이지 끝 0.5박 전 | ±1.5박 | ±1.06초 |
| **1박 (U11로 결정)** | **2박** | **페이지 끝** | **±1박** | **±0.71초** |

- 처리 지연(0.4~0.7초)은 미리 예측해서 넘기는 방식으로 보정한다(U12, 4.7절). 보정하고 남은 오차와 위치 추정 오차를 합친 값이 위 허용 오차 안에 들어와야 한다.
- 박 하나를 잘못 세면 0.71초가 어긋난다. U11에서는 박 하나만 틀려도 허용 범위 끝에 걸리므로 실패로 본다.
- 마디 하나를 통째로 틀리면(2.82초) 당연히 실패한다. 넘김 지점 부근에서는 "지금 몇 번째 박인가"가 반드시 맞아야 한다.

**템포별 허용 오차 (U11, ±1박)** (지연은 2.3절의 추정값)

| 템포 (♩) | 1박 | 허용 오차 | 정렬 지연 0.4~0.7초를 박으로 바꾸면 |
|---|---|---|---|
| 85 (시범곡) | 0.71초 | ±0.71초 | 0.6~1.0박 |
| 100 | 0.60초 | ±0.60초 | 0.7~1.2박 |
| 120 | 0.50초 | ±0.50초 | 0.8~1.4박 |
| 140 | 0.43초 | ±0.43초 | 0.9~1.6박 |
| 160 | 0.38초 | ±0.38초 | 1.1~1.9박 |

- 템포가 빠를수록 초 단위 허용 오차가 줄어든다 (R12). 보유 영상 곡들의 템포는 아직 확인하지 않았다.
- 정렬 결과를 보고 반응해서 넘기면, 지연만으로 시범곡에서 0.6~1.0박, ♩=120에서 0.8~1.4박 늦는다. 늦게 허용량 1박을 넘을 수 있다. 예측이 필요한 이유다 (U12).

| 크로마를 10 Hz로 묶기 | 약 0.05초 |
| OLTW 결과 평활 | 0.1~0.3초 |
| 네트워크 전송 (LAN. 공유 기능을 쓸 때만) | 0.01~0.05초 |
| **합계** | **약 0.4~0.7초** |

v1의 0.3~0.5초는 HPSS 지연을 빼고 계산한 값이었다. 지연은 템포로 미래 위치를 예측해서 보정할 수 있지만, 그러려면 템포 추정이 정확해야 한다. 전체 넘김을 고르면 이 예측 정확도도 검증 대상이 된다.

이 표는 정렬 경로의 지연이다 (v3.1에서 구분). 2단 구조(4.7절)에서 넘김 시각은 박 추적 경로로 계산한다. 그래서 넘김 타이밍에 직접 영향을 주는 것은 **박 감지 지연**과 **출력 지연**(넘김 명령부터 화면이 바뀔 때까지)이다. 둘 다 정렬 지연보다 짧을 것으로 보지만 측정하지 않았다 [추정]. 정렬 지연은 넘김 1~2마디 전에 하는 박 번호 확인에만 영향을 준다.

### 2.4 결론

- **연산**: 문제 없다 [추정].
- **지연**: 허용 오차 ±1박(U11)이 정렬 지연과 비슷하므로, 예측해서 미리 넘기는 방식이 필수다(U12). 박 번호가 맞으면 남는 타이밍 오차는 ±0.3박 안으로 본다 [추정, 4.7절].
- **정확도**: 확인되지 않았다. 이 프로젝트의 핵심 위험이다. U11 때문에 핵심 질문은 "넘김 지점 부근에서 박 번호를 하나도 틀리지 않는가"가 됐다.

### 2.5 실시간 엔진 요구사항 (v3.3 신규) [제안]

사용자 질문 "상당히 빠릿빠릿한 백그라운드가 있어야겠지?"에 대한 정리다. 여기서 백그라운드는 연주 중 화면 뒤에서 계속 도는 듣기·분석 엔진을 말한다. 필요한 것은 큰 연산 능력보다 **짧고 일정한 지연**이다.

| 요구 | 내용 | 근거 |
|---|---|---|
| 연산량 | 크지 않다. 마이크 쪽 처리는 휴대폰 CPU 한 코어의 1~수 %다 [추정]. 원곡 쪽 무거운 처리는 곡을 추가할 때 한 번만 한다. 신경망 박 추적은 측정이 필요하다 | 2.1절, 4.8절 |
| 지연 | 박 감지부터 화면이 바뀔 때까지가 1박보다 짧아야 한다 (♩=160이면 0.38초). 여유를 두려면 훨씬 짧아야 한다. 목표치는 Phase 2에서 잰 뒤 정한다 | 4.7절 "마지막 계산의 조건" |
| 지연의 일정함 | 처리가 순간적으로 밀리면 넘김 시각이 흔들린다. 오디오 입력, 분석, 넘김 예약, 화면 그리기를 서로 다른 스레드로 나눈다. 오디오 입력 스레드에서는 메모리 할당, 잠금, 대기를 하지 않고 링 버퍼로만 넘긴다. 넘김은 예약 시각에 정밀 타이머로 실행한다 | 실시간 오디오 프로그램의 일반 원칙 |
| 화면 넘김 | 다음 페이지와 이전 페이지를 미리 그려 둔다. PDF 한 쪽을 고해상도로 그리는 데 수십~수백 ms가 걸릴 수 있다 [추정]. 넘김 애니메이션은 없애거나 길이를 고정해서 출력 지연에 넣는다 | 4.7절 출력 지연 30 ms 가정의 전제 |
| 지속 | 합주 내내(2~3시간으로 가정) 마이크를 열고 화면을 켜 둔 채 돈다. 발열과 배터리 소모를 확인한다 | Phase 2·4에서 측정 |
| OS 백그라운드 실행 | 필요 없다. 연주 중에는 앱이 화면에 떠 있다 (U6). 대신 화면 꺼짐 방지는 필요하다 | U6 |

**v3.2 정리** [제안]: U13에 따라 B(기기마다 각자 듣기)를 기본으로 한다. A는 B의 핵심(기기 한 대가 듣고 넘기기) 위에 방송 기능만 더하면 되므로, 필요해지면 나중에 선택 기능으로 붙인다. 이때 A의 장점은 "방에서 가장 잘 들리는 자리의 기기 한 대가 듣는다"가 된다.

### 4.2 위치 표현 (D3)

U14에 따라 아래의 "기준 녹음"은 원곡이다.

**(가) 연주 마디 번호** (v1 안)
- 원곡을 실제 연주 순서대로 펼쳐서 마디에 순번(1, 2, 3 … N)을 붙인다. 반복 기호, D.S., 코다는 모두 펼쳐진 상태다.
- 파트별 넘김표는 "(연주 마디 k, 표시할 페이지)" 목록이다. 반복 때문에 앞 페이지로 돌아가는 경우도 같은 방식으로 표현된다.
- 장점: 구간 이름과 마디 번호로 위치를 지정할 수 있다.
- 단점: 원곡의 다운비트를 분석하고 사람이 검수해야 한다.

| 데이터 | 내용 | 만드는 방법 |
|---|---|---|
| 기준 마디표 | 연주 마디 k → 기준 녹음 시간(초) | All-In-One이나 Beat This!로 다운비트를 뽑고 Sonic Visualiser에서 검수 |
| 구간표 | 연주 마디 범위 → 구간 이름 | All-In-One 구조 분석 결과를 사람이 수정 |
| 기준 특징 | 크로마 시퀀스 | 미리 계산 |
| 파트별 넘김표 | (연주 마디 k, 페이지) 목록 | 멤버가 입력 |

**(나) 기준 녹음 시간 + 탭 표시** (v2 신규. CueFlip이 이 방식을 쓰는 것을 확인하고 착안했다)
- 마스터는 "기준 녹음의 몇 초 지점인가"를 방송한다.
- 각 멤버는 기준 녹음을 재생하면서 넘기고 싶은 순간에 탭해서 넘김 지점을 표시한다.
- 장점: 마디 분석이 필요 없다. 반복 기호는 탭 순서로 자연스럽게 처리된다 (보유 악보 1:03에도 반복과 세뇨가 있다, 9.1절). 넘기는 시점을 멤버가 직접 정한다.
- 단점: 구간 버튼처럼 위치를 지정하는 기능에는 구간 경계 정보가 따로 필요하다. 기준 녹음을 바꾸면 넘김 지점을 옮기거나 다시 표시해야 한다.

두 방식은 섞을 수 있다. 기본은 (나)로 하고, 구간 버튼에 필요한 구간 경계만 따로 표시하는 방법이다.

### 4.3 넘김 정책

- 페이지 전체 넘김(U10)이고, 목표 시각은 페이지 끝이다(U11). 멤버별로 넘김 시각을 조정하는 기능은 필요해지면 추가한다.
- 넘김 2마디 전에 넘길 시각을 예약하고, 박이 들릴 때마다 고친다(U12). 넘김 시각은 박 추적 결과로 계산한다 (4.7절).
- 넘기기 전 확인에서 박 번호를 믿을 수 없으면 자동으로 넘기지 않는다. 대신 화면에 "직접" 표시를 띄워 멤버가 손으로 넘길 준비를 하게 한다.
- 신뢰도가 기준값보다 낮으면 넘기지 않고 화면 가장자리에 "추적 불확실"을 표시한다.
- 수동 조작이 항상 우선이다. 다음, 이전, 처음으로(U1)를 화면 탭이나 블루투스 페달로 할 수 있게 한다.

### 4.4 추적 상태기계 (기기마다)

```

  └ 곡 선택 → ARMED (시작 대기)
       └ 첫 구간 음향 감지 또는 시작 버튼 → TRACKING
TRACKING (신뢰도 높음, 자동 넘김. 넘김마다 2마디 전부터 넘김 예측 절차를 따른다, 4.7절)
  ├ 신뢰도 하락 → UNCERTAIN (넘김 보류, 템포로 위치만 외삽)
  │     ├ 신뢰도 회복 → TRACKING
  │     └ N초 지속 → LOST
  ├ 무음 지속 (예: 3초 이상인데 기준 녹음의 같은 위치는 무음이 아님) → PAUSED
  └ 곡 끝 도달 → IDLE
PAUSED (합주 중단)
  └ 소리 재개 → LOST
LOST (전역 재탐색: 창을 3초→8초로 늘리고 구간 시작점에 가중치)
  ├ 후보 1개로 좁혀짐 → TRACKING
  └ 후보 여러 개 (반복 구간이라 구별 불가) → 화면에 후보 구간 버튼 표시, 탭으로 확정
```

### 4.5 UI 흐름 (초안)

**곡 준비 (곡마다 한 번)**
1. **곡 추가**: 원곡을 넣는다 (U14). 방법은 마이크로 듣기와 파일 넣기 두 가지다 (4.9절, D8). 마이크로 듣기를 쓰면 3번(넘김 지점 표시)과 한 번에 하므로, 2번(악보 업로드)을 먼저 한다.
   - 앱이 원곡을 미리 분석한다: 드럼 분리, 박·다운비트 격자, 정렬용 특징 (4.8절). 곡마다 한 번이다.
   - 분석은 기기에서 하는 것을 기본으로 한다 [제안]. 서버가 필요 없고 원곡을 외부로 보내지 않는다. 신경망 음원분리가 휴대폰에서 얼마나 걸리는지는 확인해야 한다. 너무 오래 걸리면 서버를 검토하고, 그때는 원곡을 올리게 되므로 저작권 문제도 함께 검토한다.
   - (가) 방식을 고르면 마디·구간 분석이 더 필요하다.
2. **파트 악보 업로드** (멤버 각자): 자기 파트 PDF를 올린다.
3. **넘김 지점 표시** (멤버 각자)
   - (나) 방식: 원곡이 나오는 동안 넘기고 싶은 순간에 탭한다. 마이크로 듣기라면 원곡을 아무 앱으로 틀어 두고, 파일 넣기라면 앱 안에서 재생한다. 탭한 시각은 가장 가까운 마디선에 맞춰 저장한다 (4.7절).
   - (가) 방식: 페이지마다 시작 마디를 입력한다. 악보에 마디 번호가 인쇄돼 있으면 OCR로 읽어서 초안을 자동으로 만들 수 있다. 띵바츄.pdf는 각 줄 첫 마디 번호가 인쇄돼 있는 것을 확인했다. 음표를 읽는 OMR은 필요 없다.
4. **미리보기 확인**: 원곡을 다시 틀어 표시한 대로 넘어가는지 본다. 마이크로 듣기라면 앱이 실제로 마이크로 따라가며 넘긴다. 입력 실수를 잡는 용도이고, 추적 정확도를 검증하는 단계는 아니다(U2). U11 때문에 넘김이 정확히 마디선에 걸리는지도 여기서 확인한다. 예측할 수 없는 넘김 지점(R13)도 이 단계에서 표시한다.

**합주 중**
- **연주 화면 (기기마다, v3.2)**: 셋리스트에서 곡을 고르고 시작한다. 연주 중에는 악보만 화면 가득 보여주고, 추적 상태를 가장자리에 작게 표시한다. 다음·이전·처음으로 조작과 구간 버튼을 지원한다. 화면 꺼짐을 막는다. 이번 넘김을 자동으로 하지 못할 때는 미리 "직접" 표시를 띄운다 (4.7절).
- **마스터 화면** (공유 기능을 붙일 때만): 셋리스트, 곡 선택, 시작·정지, 현재 구간과 위치, 신뢰도, 구간 버튼

**다음에 정할 것**: 화면별 상세 레이아웃, 반 페이지 넘김 표시 방식, 멤버 간 곡 데이터 공유 방법

### 4.6 뷰어 구현 형태 (D4, v2 신규)

**v3.2: 앱으로 정리됐다 (U6·U13).** 아래는 웹 뷰어를 뺀 이유의 기록이다.

v1에서 제안한 웹 뷰어(합주실 LAN에서 마스터 노트북이 페이지를 띄우는 방식)에는 확인된 문제가 있다.
- 화면 꺼짐 방지 기능(Screen Wake Lock API)은 HTTPS 같은 보안 연결에서만 동작한다. 마스터가 LAN에서 HTTP로 페이지를 띄우면 쓸 수 없다.
- 반대로 페이지를 HTTPS로 띄우면, LAN의 마스터에 암호화되지 않은 WebSocket(ws://)으로 접속하는 것이 브라우저 보안 정책(혼합 콘텐츠 차단)에 막힌다.
- Safari 16.4~18.4는 홈 화면에 추가한 웹 앱에서 Wake Lock이 동작하지 않는다는 버그가 보고되어 있다.

대안은 세 가지다.
1. 네이티브 앱. U1과 U6의 원래 의도에 맞는다.
2. 웹 화면을 앱으로 감싸는 방식(Capacitor 등). 화면 꺼짐 방지와 네트워크는 앱 기능으로 처리한다.
3. 프로토타입에서만 웹을 쓰고, 기기의 자동 잠금 설정을 끄는 것으로 우회한다.

### 4.7 정렬 + 박 추적 2단 구조 (v3 신규) [제안]

페이지 전체 넘김(U10)은 페이지 경계에서 박 단위 타이밍이 필요하다. 드럼이 큰 소리에서 크로마 정렬만으로 이 정확도를 꾸준히 내기는 어렵다고 본다 [추정]. 그래서 역할을 둘로 나눈다.

| 단 | 하는 일 | 쓰는 신호 | 드럼 소리의 영향 |
|---|---|---|---|
| 1단: 정렬 | 지금 기준 녹음의 어디쯤인지 파악한다 (몇 번째 마디, 몇 번째 박 근처인지) | 화성 (크로마) | 방해가 된다 |
| 2단: 박 추적 | 실제 박이 언제 울리는지와 현재 템포를 잰다 | 타악 (온셋) | 오히려 도움이 된다 |

**결합 방식**
1. **잠금**: 시작할 때와 재탐색 직후, 지금 박이 기준 녹음의 몇 번째 박인지 정한다. 방법은 두 가지다.
   - 박 단위 잠금: 정렬 결과만으로 박 번호를 정한다. 정렬 오차가 0.5박(시범곡 0.35초) 미만이어야 한다.
   - 마디 단위 잠금: 다운비트(마디 첫 박) 추적으로 마디 경계를 잡고, 정렬은 몇 번째 마디인지만 정한다. 정렬 오차가 0.5마디(시범곡 1.41초) 미만이면 된다.
   - 어느 쪽을 쓸지는 Phase 1에서 정렬 오차 분포를 보고 정한다.
2. **박 세기**: 잠금 뒤에는 박이 하나 지날 때마다 박 번호를 1씩 올린다.
3. **감시**: 정렬 결과는 박 번호가 맞는지 감시하는 데만 쓴다. 정렬 위치와 박 번호의 차이가 기준값 이상인 상태가 몇 박 동안 이어지면 다시 잠근다.
4. **넘김 명령 시각** = 마지막 박 시각 + (넘김 지점 박 번호 − 마지막 박 번호) × 박 간격 − 출력 지연
   - 마지막 박 시각은 박이 실제로 울린 시각이다. 박을 감지하는 데 걸린 시간은 여기에 이미 반영돼 있으므로 따로 빼지 않는다.
   - 출력 지연은 넘김 명령부터 화면이 바뀔 때까지의 시간이다. v3에는 "처리 지연"을 뺀다고 적었는데 틀렸다 (v3.1에서 고침).

**필요한 것**
- 기준 녹음의 박 격자: 오프라인 박·다운비트 추적(Beat This!, madmom 등)으로 자동으로 만든다. 넘김 지점 부근만 미리보기에서 사람이 확인한다. U14 이후 기준 녹음은 원곡이고, 원곡에서 분리한 드럼 트랙으로 만들면 더 정확할 것으로 본다 [추정, 4.8절].
- 넘김 지점은 박 번호로 저장한다. D3에서 (나) 방식을 고르면 탭한 시각을 박 번호로 바꿔 저장한다. 페이지는 항상 마디선에서 끝나므로 **가장 가까운 다운비트(마디 첫 박)에 맞춘다** (v3.1). 그러면 탭이 반 마디(시범곡 1.41초) 안에만 들어오면 정확한 지점이 저장된다. 가장 가까운 박에 맞추면 탭이 반 박(0.35초) 안에 들어와야 해서 실수가 생기기 쉽다.

**위험**
- 박 추적이 약한 구간이 있다. 드럼 없는 인트로, 브레이크, 필인, 템포 변화 구간이다. 이 구간에서는 정렬만으로 위치를 유지하고, 신뢰도가 낮으면 넘기지 않는다. 곡마다 넘김 지점이 이런 구간에 걸리는지 미리 확인한다 (R13).
- 박을 하나 놓치거나 하나 더 세면 그대로 0.71초 오차가 되고, U11에서는 실패다. 3번 감시 단계와 아래 넘김 예측 절차의 확인 단계에서 잡아야 한다.
- 이 구조는 v1의 접근안 A(정렬)와 B(박 세기)를 합친 것이다. B만 쓰면 한 번 틀렸을 때 복구할 방법이 없는데, A가 그 약점을 보완한다.

**넘김 예측 절차 (v3.1)** [제안]

U12("1~2마디 전부터 남은 시간을 계산해서 미리 넘긴다")를 절차로 만든 것이다.

| 시점 | 하는 일 |
|---|---|
| 넘김 2마디 전 (시범곡 약 5.6초 전) | 감시(3번) 결과를 본다. 박 번호와 정렬 위치가 일치하고 신뢰도가 기준 이상이면 넘김 명령 시각을 계산해서 예약한다. 아니면 화면에 "직접" 표시를 띄운다 |
| 그 뒤 매 박 | 새 박이 감지될 때마다 예약 시각을 다시 계산한다. 마지막 계산은 넘김 1박 전의 박이 감지된 직후다 |
| 넘김 1마디 전 | 감시 결과를 한 번 더 본다. 어긋났으면 예약을 취소하고 "직접" 표시를 띄운다 |
| 예약 시각 | 넘긴다. 그 전에 와야 할 박이 오지 않았거나(연주 중단, 브레이크) 무음이 감지됐으면 넘기지 않는다 |

- **정렬은 확인에만 쓴다.** 정렬은 지연이 0.4~0.7초이고 오차도 박 추적보다 클 것으로 본다 [추정]. 그래서 시간 여유가 있는 1~2마디 전 확인에만 쓰고, 마지막 시각 계산은 박 추적으로 한다.
- **매 박 다시 계산하는 이유**: 2마디 전에 한 번만 계산하면, 템포 추정이 5% 틀릴 때 8박 동안 0.4박이 어긋난다. 마지막 계산을 1박 전에 하면 같은 조건에서 0.05박이다 [추정].
- **마지막 계산의 조건**: 넘김 1박 전의 박을 감지한 뒤에 명령을 내려야 하므로, 박 감지 지연과 출력 지연의 합이 1박보다 짧아야 한다. ♩=160이면 0.38초다.
- **"직접" 표시**: 2마디 전에 띄우면 멤버는 약 2마디 동안 손으로 넘길 준비를 할 수 있다. 자동 넘김을 포기한 횟수는 따로 센다 (6장).
- 2마디 전이 적당한지(1마디 전과 비교)는 실험으로 정한다 (7장).

**타이밍 오차 예산 (박 번호가 맞을 때)** [추정]

| 원인 | 크기 | 비고 |
|---|---|---|
| 박 시각 오차 (박 추적) | ±70 ms 안이라고 가정 | 시범곡에서 0.1박, ♩=160에서 0.19박 |
| 템포 오차 | 약 0.05박 | 마지막 계산이 1박 전이고 템포 오차가 5%일 때 |
| 출력 지연 보정 후 남는 오차 | 약 30 ms로 가정 | 기기마다 각자 들으면 네트워크를 거치지 않는다. 공유 기능에서도 박 시계 방송을 쓰면 네트워크 지연은 들어가지 않는다. 다음 페이지를 미리 그려 둔다는 전제다 (2.5절) |
| 합계 (최악의 경우를 더함) | 약 0.2박(시범곡) ~ 0.3박(♩=160) | 허용 ±1박 안 |

박 번호가 하나 틀리면 여기에 1박이 그대로 더해져 허용 범위 끝에 걸린다. 그래서 U11에서 정확도의 핵심은 타이밍이 아니라 **박 번호**다.

**박 시계 방송 (공유 기능을 붙일 때)** [제안]

- 마스터는 매 박 "박 번호 b가 시각 t에 울렸고, 박 간격은 T이고, 감시 결과는 일치/불일치"를 방송한다.
- 각 기기는 자기 파트의 넘김 지점(박 번호)으로 자기 넘김 시각을 계산한다. 멤버마다 페이지가 나뉘는 위치가 달라도(U3) 마스터는 각 파트의 넘김 지점을 몰라도 된다.
- 넘김 시각은 박이 울린 시각으로 계산하므로 와이파이 전송 지연은 넘김 타이밍에 들어가지 않는다. 마지막 박 정보가 늦게 오면 그 전 박 정보로 계산한 시각에 넘긴다. 이때는 계산 거리가 2박이라 템포 오차가 0.1박 정도로 커진다 [추정].
- 대신 기기 사이 시계를 맞춰야 한다. LAN에서 시각을 주고받아 차이를 재는 방식(NTP와 같은 원리)을 쓴다. 필요한 정확도는 수십 ms다.

### 4.8 원곡 기준 정렬 (v3.3 신규) [제안]

U14로 기준은 원곡이다. 정렬은 "내장 마이크로 들은 합주실 소리"를 "스튜디오 원곡"에 맞춰야 한다.

| 차이 | 합주실 (실시간, 내장 마이크) | 원곡 (미리 처리) | 대응 |
|---|---|---|---|
| 드럼 | 매우 크다 | 다른 악기와 균형 있게 섞여 있다 | 원곡에서 드럼을 분리한다. 화성 비교에는 드럼을 뺀 원곡을, 박·패턴 비교에는 드럼 트랙을 쓴다. 마이크 쪽은 인과적 HPSS로 화성 성분과 타악 성분을 나눈다 |
| 화성 악기 | 앰프와 자리에 따라 크기가 다르다 | 믹싱으로 균형이 잡혀 있다 | 로그 압축, 크로마 정규화 |
| 원곡에만 있는 소리 | 없다 | 신스, 오버더빙, 코러스 | 분리 트랙 조합을 바꿔 가며 실험한다 (7장) |
| 템포 | 흔들리고, 원곡과 다를 수 있다 | 고정 | OLTW 기울기 제약, 박 추적 템포 (4.7절) |

**처리를 비대칭으로 한다**
- 원곡 쪽은 곡을 추가할 때 한 번만 처리한다. 실시간 제약이 없으므로 신경망 음원분리, 오프라인 박·다운비트 분석 같은 무거운 처리를 쓸 수 있다.
- 실시간 제약은 마이크 쪽에만 있다 (2.1절).

**드럼을 단서로도 쓴다**
- 멤버들이 원곡대로 연주하므로(U5) 드러머도 원곡과 비슷한 패턴과 필인을 친다고 본다 [추정].
- 그래서 드럼은 화성 비교에는 방해가 되지만, 두 가지로 정렬을 도울 수 있다.
  1. 박 추적: 박 시각과 템포 (4.7절)
  2. 드럼 패턴 비교: 원곡 드럼 트랙과 마이크 입력의 타악 성분에서 대역별(킥·스네어·심벌) 온셋 패턴을 뽑아 비교한다. 필인과 크래시 심벌은 구간 경계에 자주 오므로 위치 단서가 된다 [추정]. 같은 리듬이 반복되는 구간 안에서는 단서가 약하다.
- 화성 특징과 드럼 패턴 특징을 섞는 비율은 Phase 1에서 정한다 (7장).

**Phase 1의 첫 질문**
- 원곡 기준 정렬 오차가 0.5박(시범곡 0.35초) 미만이면 박 단위 잠금을 쓴다. 0.5마디(1.41초) 미만이면 다운비트 추적과 함께 마디 단위 잠금을 쓴다 (4.7절). 원곡 기준에서 어느 쪽이 나오는지가 Phase 1의 첫 질문이다.

**더 조사할 것**
- 드럼이 있는 라이브 밴드 소리를 스튜디오 원곡에 실시간으로 맞춘 연구와 구현. 1차 조사에서는 찾지 못했다 (0장).
- 커버곡 정렬(오프라인), 타악 특징을 쓴 정렬, 대중음악 라이브 동기화(Dannenberg 2014)

### 4.9 원곡 넣기와 저작권 (v3.4 신규) [제안]

U14 때문에 원곡은 꼭 필요하다. D3에서 어느 방식을 고르든 앱이 원곡과 비교해서 위치를 찾기 때문이다. 사용자가 지적한 두 문제(원곡 준비 부담, 저작권. U15)를 다음처럼 다룬다.

**원곡을 넣는 두 가지 방법 (D8)**

| | 마이크로 듣기 | 파일 넣기 |
|---|---|---|
| 방법 | 원곡을 아무 앱(멜론, 스포티파이, 유튜브 등)으로 틀어 두면 앱이 마이크로 듣는다 | 사용자가 가진 음원 파일을 앱에 넣는다 |
| 원곡 준비 | 파일이 필요 없다. 스트리밍만 써도 된다 | 파일을 구해야 한다. 스트리밍 앱에서 내려받은 곡은 보통 보호돼 있어 다른 앱이 읽을 수 없다 |
| 넘김 지점 표시 | 듣는 동안 탭한다. 원곡 준비와 한 번(곡 길이, 3~5분)에 끝난다 | 앱 안에서 재생하며 탭한다 |
| 기준 품질 | 스피커와 방 소리가 섞인다. 휴대폰 스피커는 저음이 약하다 (R14) | 가장 좋다 |
| 남기는 것 | 분석이 끝나면 녹음을 지우고 분석 결과만 남긴다 | 분석과 탭이 끝나면 앱 안의 복사본을 지우고 분석 결과만 남긴다 |

- 마이크로 듣기는 연주 중에 쓰는 마이크 입력을 그대로 쓰고, 그 뒤 분석 과정은 파일 넣기와 같다. 그래서 두 방법을 다 지원해도 추가로 만들 것이 적다 [추정].
- 마이크로 듣기라면 미리보기(4.5절 4번)도 원곡을 다시 틀어 두고 앱이 실제로 따라 넘기는지 보는 방식이 된다. 넘김 지점 확인용이고, 합주실 정확도 검증은 아니다 (U2).

**저작권 부담을 줄이는 원칙** [제안. 법률 판단이 아니다]
1. 앱은 음악을 제공하지 않는다. 사용자가 이미 들을 수 있는 원곡을 자기 기기에서 분석만 한다.
2. 분석은 기기 안에서 한다. 서버로 원곡을 올리지 않는다 (4.5절).
3. 원곡 소리는 저장하지 않고, 다른 멤버나 다른 기기로 보내지 않는다. 나중에 공유 기능을 붙여도 분석 결과(박 위치, 화성·드럼 패턴 특징, 넘김 지점)만 보낸다. 분석 결과로는 원곡을 다시 들을 수 없다 [추정].
4. 앱을 공개 배포한다면 그 전에 법률 검토를 받는다.

## 5. 알고리즘 상세 [제안, 초기 후보값. 실험으로 확정]

| 단계 | 초기 설정 | 실험할 대안 |
|---|---|---|
| 입력 | 기기 내장 마이크(U13), OS 음성 처리 끔(R8), 22.05 kHz 모노로 변환 | 기기 자리와 방향 |
| STFT | 창 4096, hop 512 (약 23 ms) | 창 2048, CQT |
| 타악 억제 | 짧은 hop에서 인과적 HPSS (시간축 중앙값 필터는 과거 약 0.5초만 사용) | HPSS 없음, 신경망 음원분리 (후순위. 연산량 측정 필요) |
| 크로마 | 로그 압축 → 12 bin → 10 Hz로 묶기 → L2 정규화. 무음 처리를 위해 음량 차원을 추가 | CENS, 대역 제한, 튜닝 보정 |
| 정렬 | OLTW (Dixon 2005), 탐색 폭은 기준 녹음 30초. **직접 구현**한다. matchmaker는 악보(MusicXML/MIDI) 기준 피아노 추종 라이브러리라서 참고 구현으로만 쓴다 | Windowed Time Warping (Macrae 2010), matchmaker의 "arzt" 방식(Brazier & Widmer 2020을 변형한 OLTW) |
| 박 추적 (v3부터 핵심) | 실시간 박·다운비트 추적: BeatNet. 템포 범위는 기준 녹음 템포 근처로 제한한다 (R12) | BTrack, aubio, madmom 온라인 모드 |
| 기준 녹음 박 격자 | 오프라인 박·다운비트 추적: Beat This! | madmom, All-In-One |
| 결합 | 정렬로 잠그고 박을 센다. 정렬은 감시에 쓴다 (4.7절) | 다운비트 기준 마디 단위 잠금 |
| 넘김 예측 (v3.1) | 넘김 2마디 전에 확인하고 예약, 매 박 갱신, 1마디 전에 다시 확인 (4.7절) | 1마디 전부터. 한 번만 계산 |
| 원곡 전처리 (v3.3) | 신경망 음원분리(Demucs 계열)로 드럼 분리 → 드럼 뺀 원곡의 크로마, 드럼 트랙의 대역별 온셋, 박·다운비트 격자 (4.8절) | 분리 트랙 조합 (보컬 포함·제외 등) |
| 드럼 패턴 특징 (v3.3) | 대역별(킥·스네어·심벌) 온셋 패턴. 마이크 쪽은 인과적 HPSS의 타악 성분에서 뽑는다 | 쓰지 않음 (크로마만) |
| 재탐색 | 최근 3초 → 5초 → 8초로 창을 늘려 가며 subsequence DTW를 한다. 1위와 2위 점수 차가 기준 이상이면 확정한다 | 구간 시작점 가중치 |
| 신뢰도 | DTW 경로 비용의 최근 이동평균 + 재탐색 결과의 1위·2위 점수 차 | 학습 기반 보정 |

## 6. 검증 계획 [제안]

일정은 주당 투입 시간이 정해지면 잡는다. v1에 적었던 "1~2주" 같은 기간은 근거가 없어서 뺐다.

### Phase 0. 보유 데이터 정리

- 시범곡 Think About'chu 영상에 곡 시작과 끝 시각을 표시하고, 길이 차이의 원인을 확인한다 (R11).
- **정답 마디표는 사람이 만든다.** 박에 맞춰 탭한 뒤 Sonic Visualiser에서 수정한다. 자동 정렬 결과를 정답으로 쓰지 않는다. 그렇게 하면 평가 대상과 같은 계열의 방법으로 정답을 만드는 셈이 되기 때문이다.
- 부족한 것을 확인한다: 다른 곡의 원곡 음원, 재시작이 들어간 녹음, 녹음 기기와 위치 정보.
- 보유 영상 곡들의 템포를 확인한다 (R12). 보유 악보에서 페르마타나 브레이크에 걸린 넘김 지점을 센다 (R13).

### Phase 0.5. 기존 앱으로 핵심 위험 먼저 확인 (D6, v2 신규)

- CueFlip(무료로 시작 가능, iPad/iPhone)이나 Score Flip(미국 스토어 $8.99)에 시범곡을 등록해서 합주실에서 써 본다.
- CueFlip은 사용자가 한 번 연주하는 동안 녹음해서 그것을 기준으로 쓴다. 합주 녹음이나 원곡을 기준으로 넣을 수 있는지는 확인해야 한다.
- U14 때문에 원곡을 기준으로 넣을 수 있는 앱만 같은 조건의 비교가 된다. 넣을 수 없는 앱은 요구 자체가 다르다.
- 결과 해석
  - 잘 되면: 드럼 환경의 정확도 위험은 낮다. 이 경우 차별점은 여러 기기 공유(4.1의 A)로 좁혀진다.
  - 안 되면: 드럼 환경 문제가 실제로 있다는 것을 확인한 셈이다. 직접 만들 이유가 분명해진다.
- 한계: 기존 앱의 내부 방식을 모르기 때문에 결과는 참고용이다.

### Phase 1. 오프라인 인과 시뮬레이션 (실현 가능성 판정)

- 합주 녹음을 프레임 순서대로 흘려 넣고, 미래 프레임은 쓰지 않는다. 그러면 알고리즘의 판단은 실시간과 같다.
- 다만 녹음 위치, 녹음 기기, 자동 음량 조절, 실시간 처리 일정은 반영되지 않는다(R8). 이 부분은 Phase 2에서 확인한다.
- 시범곡 1곡(넘김 5회)으로는 판정하지 않는다. 최소 3곡, 넘김 15회 이상으로 판정한다.
- 악보가 없는 곡은 모든 마디선을 넘김 후보로 보고 박 번호 정확도를 잰다 [제안, v3.6]. 실제 페이지보다 시험 지점이 훨씬 많다. 실제 페이지 끝 위치에서의 평가는 악보가 있는 곡(띵바츄, 1:03)으로 한다. 그래서 Phase 1을 위해 악보를 더 구할 필요는 없다. 대신 곡마다 원곡 음원이 필요하다 (U14).
- 재시작은 녹음을 잘라 붙여 흉내 낸 합성 시험으로 먼저 보고, 실제 재시작 녹음으로 따로 확인한다.

**통과 기준 (넘김 방식별, 사용자와 합의 필요)**

| 지표 | 통과 기준 (페이지 전체 넘김) |
|---|---|
| 잘못 넘김 (엉뚱한 페이지) | 0회 |
| 넘김 시각이 허용 범위(페이지 끝 ±1박, U11)를 벗어난 횟수 | 15회 중 1회 이하 |
| 자동으로 넘기지 않고 "직접" 표시로 돌린 횟수 (v3.1) | 15회 중 2회 이하 [제안] |
| 재시작 후 재정렬 시간 | 4마디 이내 |

판정과 별도로, 원인을 찾기 위해 다음 값을 기록한다.
- 정렬 오차 분포: 대부분 0.5박 미만이면 박 단위 잠금을, 아니면 마디 단위 잠금을 쓴다 (4.7절).
- 박 추적 정확도: 정답 박에서 ±70 ms 안에 들어온 비율. 박 추적 평가에서 흔히 쓰는 기준이다.
- 넘김 준비 시점의 박 번호 오류: 오류가 있었을 때 확인 절차가 잡았는지("직접" 표시로 돌림), 놓쳤는지(틀린 시각에 넘김) 나눠 센다.
- 넘김 타이밍 오차 분포: 박 번호가 맞은 넘김만 모아서 4.7절의 추정(±0.3박 안)과 비교한다.

v1의 "98% 이상"은 넘김 15~30회 규모에서는 의미가 없었다. 30회 중 1회만 실패해도 96.7%가 되기 때문이다. 그래서 횟수로 바꿨다.

**실패하면 이 순서로 시도한다**
1. 원곡 쪽 처리를 바꾼다: 분리 트랙 조합, 드럼 패턴 특징의 비중 (4.8절).
2. 잘 들리는 자리의 기기 한 대가 듣고 다른 기기에 공유한다 (4.1절의 A). 믹서 출력은 쓰지 않는다 (U13).
3. 마이크 쪽에서도 신경망 음원분리로 드럼을 제거한다 (연산량 측정 포함).
4. 요구 수준을 낮춘다. 일찍 허용량을 늘리거나(U11 변경), 반 페이지 넘김을 쓰거나(U10 변경), 합주 녹음을 기준에 더한다(U14 변경, R2-b). 모두 사용자가 정한 것이므로 사용자 동의가 있어야 한다.
5. 그래도 안 되면 반자동으로 줄인다. 박 추적으로 마디를 세고, 위치는 구간 탭으로 보정한다.

### Phase 2. 실시간 프로토타입

- 맥북(대상 기기 중 하나, U13)의 내장 마이크로 Python 실시간 처리를 하고, 같은 맥북 화면에서 악보를 넘긴다.
- 측정 항목: 처리 지연, 실제 보면대 자리에서의 정확도(R8), 멤버가 불편했던 순간

### Phase 3. 견고성

- 상태기계 전체(PAUSED, LOST, 구간 탭), 신뢰도 기준값 조정, 셋리스트

### Phase 4. 모바일 앱으로 이식 (Phase 2·3이 성공했을 때만)

- 핵심 처리(HPSS, 크로마, OLTW, 박 추적)를 C++로 다시 구현해 iOS와 Android에서 같이 쓴다.
- 오디오 입력은 각 OS 기본 기능(AVAudioEngine, Oboe)을 쓰고, OS 음성 처리를 끄는 입력 모드로 연다 (R8).
- 아이패드 앱은 Apple Silicon 맥에서도 실행할 수 있으므로, 맥북은 아이패드 앱으로 지원하는 방안을 먼저 확인한다 (U13) [확인 필요: 마이크 입력과 화면 동작. Intel 맥은 해당 없음].
- 배포를 생각하면 GPL/AGPL 라이브러리(aubio, Essentia, BTrack, MATCH 원본)는 쓰지 않는다.

## 8. 평가 지표

- **위치 오차**: 매 시점의 (추정 위치 − 정답 위치)를 박 단위와 마디 단위로 잰다.
- **넘김 판정**: 넘긴 시각(화면이 바뀐 시각)이 [페이지 끝 − 1박, 페이지 끝 + 1박] 안에 있으면 정답이다 (U11). 반 페이지 넘김을 대안으로 시험할 때는, 각 단계가 해당 절반을 연주하는 시간 안에서 일어나면 정답이다.
- **박 추적 정확도** (진단용): 정답 박에서 ±70 ms 안에 들어온 추정 박의 비율
- **정렬 오차** (진단용): 정렬 위치와 정답 위치의 차이를 박 단위로 잰 분포
- **넘김 타이밍 오차** (v3.1): (넘긴 시각 − 페이지 끝)을 박 단위와 초 단위로 잰 분포
- **자동 포기** (v3.1): 자동으로 넘기지 않고 "직접" 표시로 돌린 횟수
- **잘못 넘김**: 정답이 아닌 페이지로 넘긴 횟수
- **늦은 넘김 / 놓친 넘김**: 허용 범위 뒤에 넘겼거나 아예 넘기지 않은 횟수
- **재정렬 시간**: 재시작 후 위치 오차가 0.5마디 안으로 돌아오기까지 걸린 마디 수
- **처리 지연**: 오디오 입력부터 화면 넘김까지 걸린 시간 (Phase 2에서 측정)

**남은 차별점**
1. 드럼을 포함한 밴드 전체 소리에서 동작한다고 밝힌 제품이나 연구는 확인되지 않았다.

3. 반대로, 녹음을 기준으로 소리를 듣고 넘기는 기술 자체는 새롭지 않다(CueFlip, Score Flip).

## 14. 성공 가능성 판단 (v3.5) [추정]

사용자 질문 "구현 성공 가능성은 얼마나 되지? 높일 수 있는 방법은? 현실적으로."에 대한 판단이다. 측정값이 아니라 주관적 추정이다.

**결론**: 현재 결정(U10~U15) 그대로 Phase 1 통과 기준(6장)을 첫 시도에 맞출 가능성은 20~30%로 본다. 이 숫자의 대부분은 "아직 측정하지 않아서 모른다"에서 나온다.

| 부분 | 가능성 | 이유 |
|---|---|---|
| 실시간 처리 | 높음 (90% 이상) | 연산량이 작다 (2.1절). 모바일 실시간 오디오 처리는 흔한 기술이다 |
| 박 타이밍 | 높음~중간 | 드럼이 크게 들려 박은 잘 잡힐 것으로 본다. 필인, 브레이크, 빠른 곡에서 흔들린다 (R12) |
| 원곡과 마디 단위로 맞추기 | 중간 | 드럼 있는 밴드 소리를 원곡에 실시간으로 맞춘 사례를 찾지 못했다. 마디 단위(시범곡 ±1.4초)라면 될 가능성이 꽤 있다고 본다 |
| 넘김 직전 박 번호 0오류 | 낮음~중간 | ±1박(U11)이라 박 하나만 틀려도 실패한다. 가장 어려운 부분이다 |
| 사이드 프로젝트로 앱 완성 | 중간 | 기술적으로는 가능하지만 일이 많다: C++ 처리부, iOS·안드로이드 앱, 신경망 모델 |

**결정을 바꾸지 않고 높이는 방법** [제안]
1. 앱을 만들기 전에 보유 데이터로 먼저 잰다 (Phase 1, 가장 효과가 크다). 시범곡 영상, 원곡 분리 트랙, 악보로 노트북에서 오프라인 실험을 한다. 이 측정 하나로 위 추정이 크게 바뀐다. 박 단위로 맞으면 50% 이상, 마디 단위도 안 되면 10% 미만으로 본다. 그만둘 기준과 방향을 바꿀 기준을 미리 정해 둔다.
2. 드럼으로 박 번호 오류를 잡는다. 대부분의 록·팝은 스네어가 2·4박에 온다. 박을 하나 잘못 세면 스네어 위치가 어긋나므로, 원곡 드럼 패턴과 비교해서 바로 알아챌 수 있다고 본다 [추정] (4.8절).
3. 틀릴 것 같으면 넘기지 않는다. 2마디 전 확인과 "직접" 표시(4.7절)로, 실패를 "엉뚱한 페이지"가 아니라 "이번엔 손으로 넘김"으로 바꾼다.
4. 실제 조건 데이터를 모은다. 합주 때 휴대폰이나 아이패드를 보면대 위에 두고 녹음한다. 드럼 옆 자리를 포함한다. 보유 영상은 녹음 조건을 모른다 (R8).
5. 범위를 좁혀서 시작한다. 드럼이 꾸준한 4/4 곡과 보통 템포부터 한다. 기기는 아이패드 하나로 먼저 만든다 (Apple Silicon 맥북은 아이패드 앱으로 따라올 수 있다, 확인 필요). 앱보다 맥북 Python 시제품(Phase 2)을 먼저 만든다.

**결정을 바꾸면 크게 오르는 방법** (사용자 동의가 있어야 한다)

| 바꿀 것 | 효과 | 이유 |
|---|---|---|
| 두 번째 합주부터 우리 합주 녹음을 기준에 더한다 (D5를 c로) | 크다 | 첫 합주만 원곡으로 버티면 된다. 같은 기기, 같은 자리 녹음이라 맞추기 쉽다 |
| 마지막 마디 시작부터 넘겨도 되게 한다 (D7을 a로) | 크다 | 허용 오차가 ±2.5박이 되어 박 1~2개를 잘못 세도 범위 안이다 |
| 반 페이지 넘김 (U10 변경) | 가장 크다 | 허용 오차가 약 10마디가 되어 마디 단위 정확도면 충분하다 |
| "직접" 허용 횟수를 늘린다 (통과 기준 변경) | 중간 | 자동으로 넘기는 비율은 낮아지지만 쓸 수는 있다 |

**권장**: 결정은 그대로 두고 1번(먼저 재기)부터 한다. 결정을 바꿀지는 측정 결과를 보고 판단한다. 실행 시작은 사용자가 정한다 (U8).
