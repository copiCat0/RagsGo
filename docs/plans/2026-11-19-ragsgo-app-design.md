## 0. 요약

- **앱은 엔진, 기기 계층, 화면의 세 부분이다.**
  - 엔진: 듣기와 분석. C++로 만들어 모든 기기가 같이 쓴다.
  - 기기 계층: 마이크, 음원 파일 읽기, PDF 그리기, 시계.
  - 화면: 곡 목록, 곡 준비, 파트 준비, 연주, 설정.
- **엔진과 기기 계층은 네이티브여야 한다** (사용자 판단과 같다). 마이크를 OS의 말소리 처리 없이 열어야 하고, 분석이 멈추지 않고 짧고 일정한 지연으로 돌아야 하기 때문이다.
- **첫 기기는 안드로이드다.** 화면은 Kotlin + Jetpack Compose로 만든다 [제안]. 아이패드·아이폰·맥은 같은 엔진에 화면만 따로 붙인다.
- **엔진은 Phase 1-b의 Python 처리(약 700줄)를 옮긴다.** 같은 소리 파일을 넣었을 때 Python과 같은 결과가 나오는지로 확인한다.
- **자동 넘김은 바로 켜지 않는다** [제안]. 아래 순서로 간다. 합주할 때마다 실제 조건 자료(R8)가 쌓인다.
  1. 기록 모드: 악보를 손으로 넘기면서 보면대 자리 소리와 넘긴 시각을 저장한다.
  2. 예측 모드: 엔진이 넘길 시각을 계산해서 표시·기록만 하고 넘기지는 않는다. 사람이 넘긴 시각과 비교한다.
  3. 자동 넘김: 예측 모드 결과가 기획의 통과 기준(기획 6장)을 맞추면 켠다.
- 기획의 Phase 2(맥북 Python 시제품)는 위 1~2단계로 대신하는 것을 제안한다. Phase 1 판정(원곡 3곡)은 그대로 필요하다.
- **원곡 소리는 앱에 남기지 않는다** (U15, P14). 원곡 파일은 분석할 때만 읽고 분석 결과만 저장한다. 멤버끼리는 소리가 없는 "곡 패키지"만 주고받는다.
- **엔진에 아직 없는 기능이 있다.** 원곡에서 마디 첫 박 찾기, 원곡이 파일 하나일 때 드럼 줄이기, 펼친 쪽으로 재시작 범위 좁히기다. 앱보다 Python 실험을 먼저 한다 (8절).
- **개발 도구는 이미 깔려 있다** (Android Studio, SDK 36, NDK 28, CMake). 디스크 여유가 1.9 GB뿐이라 안드로이드 빌드 전에 정리해야 한다 (12절).

## 3. 사용 장면

### 3.1 곡 준비 (곡마다 한 번, 멤버 한 명)

1. 곡을 추가하고 원곡 파일을 고른다. 악보에 적힌 템포(예: ♩=85)를 넣으면 분석이 더 안정된다 (선택).
2. 앱이 기기 안에서 원곡을 분석한다. 수십 초 안으로 본다 [추정].
3. 결과를 본다: 템포, 박자, 마디 수, 드럼이 약한 대목.
4. (선택) 원곡을 들으며 구간 시작(1절, 후렴 등)을 탭한다. 재시작 버튼에 쓴다.
5. 곡 패키지를 다른 멤버에게 파일로 보낸다 (메신저, 드라이브 등). 소리는 들어 있지 않다.

### 3.2 파트 준비 (멤버마다, 곡마다 한 번)

1. 곡 패키지를 열거나 3.1을 직접 한다.
2. 자기 파트 PDF를 넣는다.
3. 원곡을 처음부터 들으며 넘기고 싶은 순간에 화면을 탭한다. 탭하면 실제로 다음 쪽으로 넘어간다. 반복 기호 때문에 앞 쪽으로 가야 하면 쪽 번호를 고른다.
   - 원곡 파일이 이 기기에 있으면 앱 안에서 재생한다.
   - 없으면 원곡을 다른 기기나 스트리밍 앱으로 틀고 앱이 마이크로 따라간다 (D8, 멤버 배포 전에 만든다).
4. 앱은 탭한 시각을 가장 가까운 마디 첫 박에 맞춰 저장한다 (기획 4.7절).
5. 미리보기로 넘김 지점마다 2마디 전부터 들으며 제때 넘어가는지 본다. 어긋나면 한 마디 앞이나 뒤로 옮긴다. 자동으로 넘기기 싫은 지점은 "직접"으로 바꾼다.

### 3.3 합주

1. 셋리스트에서 곡을 고르면 악보 첫 쪽이 뜨고 앱이 듣기 시작한다.
2. 연주가 시작되면 앱이 박을 잡고 원곡 위치를 따라간다. 스틱 카운트는 곡의 박으로 세지 않는다 (Phase 1-b).
3. 넘김 2마디 전에 넘김을 예약하고 페이지 끝에서 넘긴다.
4. 자신이 없으면 2마디 전에 "직접" 표시를 띄우고 넘기지 않는다.
5. 연주가 멈추면 앱도 멈춤 상태가 된다. 다시 칠 쪽을 펼쳐 두거나 구간 버튼을 누르면, 다시 칠 때 그 범위에서 위치를 찾는다.
6. 곡이 끝나면 버튼으로 다음 곡으로 넘어간다.

### 3.4 문제가 생겼을 때

- 손 조작이 항상 우선이다. 손으로 넘기면 그 지점의 자동 넘김은 건너뛴다.
- 앱이 엉뚱하게 따라가면 화면을 길게 눌러 자동 넘김을 끈다. 듣기와 기록은 계속한다.
- 전화 같은 다른 앱이 마이크를 가져가면 "듣기 끊김"을 표시한다. 마이크가 돌아오면 멈춤 상태에서 다시 시작한다.

### 5.2 연주 화면 [제안]

```
+--------------------------------------
| ● 따라감  23마디               3/6쪽     <- 상태 한 줄 (작게)
|
|
|              (악보 3쪽)
|
|
|                               [ 직접 ]   <- 자동으로 안 넘길 때만, 넘김 2마디 전부터
| ■■■■■■■■■■□□□□□□□□□□□□                   <- 넘김 예약 막대 (예약된 2마디 동안 찬다)
+--------------------------------------
  왼쪽 1/3 탭 = 이전 쪽 · 오른쪽 1/3 탭 = 다음 쪽 · 가운데 길게 누르기 = 메뉴
```

- 화면 거의 전부를 악보에 쓴다. 상태는 위쪽 가장자리 한 줄에 작게 둔다.

| 상태 | 표시 |
|---|---|
| 기다림 | 회색 점, "시작 기다림" |
| 따라감 | 초록 점, 마디 번호 |
| 자신 없음 | 노란 점. 다가오는 넘김은 "직접" |
| 멈춤 | 회색 점, 아래에 재시작 패널 (5.3절) |
| 듣기 끊김 | 빨간 점, "마이크 끊김" |

- 넘김 예약 막대: 자동 넘김이 예약되면 아래쪽 가장자리의 가는 막대가 2마디 동안 찬다. 멤버가 "곧 넘어간다"를 알 수 있다 [제안].
- "직접" 표시: 자동으로 넘기지 않을 넘김 2마디 전부터 오른쪽 아래에 크게 띄운다. 깜빡이지 않는다.
- 메뉴: 처음으로, 자동 넘김 끄기·켜기, 기록 시작·끝, 다음 곡.
- 화면 꺼짐을 막는다. 화면 방향은 파트 준비 때 정한 방향으로 고정한다.

### 5.3 멈춤과 재시작 [제안, 8절 E3 실험 뒤 확정]

```
+--------------------------------------
| ○ 멈춤                         3/6쪽
|
|              (악보 3쪽)
|
+--------------------------------------
| 다시 칠 곳:  이 쪽 (기본)
| [처음부터]  [1절]  [후렴1]  [B]  ...
+--------------------------------------
```

- 연주가 멈추면 (Phase 1-b 기준: 0.6초 평균이 20 dB 떨어짐) 화면 아래에 패널이 뜬다.
- **기본은 "지금 펼친 쪽"이다.** 멤버는 보통 다시 칠 쪽을 펼쳐 두므로 따로 누를 필요가 없다. 다시 칠 때 그 쪽이 보이는 박 범위 안에서 위치를 찾는다.
- 구간 버튼을 누르면 그 구간 첫 박에서 다시 시작한다고 본다. Phase 1-b의 탭 시험과 같은 조건이다 (19/19가 1박 안).
- "펼친 쪽" 방식은 아직 시험하지 않았다. 반복이 많은 곡은 한 쪽 안에도 같은 화성이 여러 번 나온다 (띵바츄는 8마디 화음이 곡 내내 반복). Python으로 먼저 잰다 (8절 E3).
- 힌트 없이 다시 찾았을 때는 몇 마디 동안 자동으로 넘기지 않는다 (잘못 잠김 방지, Phase 1-b. 길이는 8절 E4).
- 멤버마다 기기가 따로 듣기 때문에, 재시작 힌트도 멤버마다 따로 준다. "펼친 쪽"을 기본으로 둔 이유다.

### 5.4 파트 준비: 넘김 지점 표시 [제안]

```
+--------------------------------------
| ▶ 0:37 / 4:41                [되돌리기]
|
|              (악보 1쪽)
|
|        넘길 때 화면을 탭하세요
+--------------------------------------
| 쪽:  [1]  2   3   4   5   6             <- 앞 쪽으로 갈 때(반복, D.S.) 고른다
+--------------------------------------

결과: 1→2쪽  15마디 첫 박 (0:39)   [한 마디 앞] [한 마디 뒤] [직접]
      2→3쪽  35마디 첫 박 (1:35)   ...
```

- 원곡이 재생되는 동안 연주할 때처럼 넘기고 싶은 순간에 탭한다. 탭하면 다음 쪽으로 넘어가고 시각이 기록된다.
- 탭은 가장 가까운 마디 첫 박에 맞춘다. 반 마디(띵바츄 1.41초) 안에만 들어오면 정확한 지점이 된다 (기획 4.7절).
- 미리보기 "넘김 지점만 듣기": 넘김마다 2마디 전부터 3마디를 틀고 앱이 넘긴다. 곡 전체를 다시 듣지 않아도 된다.
- 원곡 분석에서 드럼이 약한 대목에 걸린 넘김은 앱이 "직접 권장"으로 미리 표시한다 (Phase 1-b 결과 문서 10절 6번 (가)).

### 5.5 곡 준비 [제안]

- 원곡 파일 고르기: mp3, m4a, flac, wav 등. 스트리밍 앱에서 내려받은 보호된 파일은 읽을 수 없다 (기획 4.9절).
- (선택) 악보에 적힌 템포. 템포를 절반이나 두 배로 잘못 잡는 것을 막는다 (R12).
- 분석 결과: 템포, 박자, 길이, 마디 수, 첫 박 위치, 드럼이 약한 대목.
- 결과가 이상하면(템포가 절반 등) 템포를 고쳐 다시 분석한다.

### 5.6 설정

- 입력 확인: 음량 막대, 찌그러짐 횟수, 입력 모드("말소리 처리 꺼짐" 또는 대체 모드) 표시
- 넘김 시점 조정: 전체를 조금 앞당기거나 늦춘다
- 기록: 연주 소리 저장 켜기·끄기, 기록 내보내기
- 개발자 설정: 엔진 기준값 (박 세기 하한, 정렬 여유 기준 등)

## 6. 추적 상태와 넘김 규칙

### 6.1 상태 [제안, 기획 4.4절을 Phase 1-b 결과로 고침]

```
기다림 (곡 선택, 소리 기다림)
  └ 연주 시작 감지 (소리 상승 + 박) → 따라감
따라감 (자동 넘김 가능)
  ├ 확인 실패 (박 세기 약함, 정렬 여유 작음) → 자신 없음 (자동 넘김 보류, "직접")
  │     └ 회복 → 따라감
  ├ 소리 멈춤 → 멈춤
  └ 곡 끝 → 끝
멈춤 (재시작 패널)
  └ 소리 다시 남 → 다시 찾기 (힌트: 펼친 쪽 / 구간 버튼 / 처음부터)
다시 찾기
  └ 박 번호가 연속으로 안정 → 따라감 (힌트 없이 찾았으면 더 오래 확인)
듣기 끊김 (마이크를 잃음)
  └ 마이크 돌아옴 → 멈춤
```

### 6.2 넘김 규칙

1. 넘김 2마디 전: 최근 박 번호가 1씩 고르게 오르고, 지난 박들의 박 세기 평균이 0.4 이상이고, 정렬 여유가 기준 이상이면 넘김 시각을 예약한다. 아니면 "직접"을 띄운다 (Phase 1-b 설정값).
2. 매 박: 예약 시각 = 마지막 박 시각 + 남은 박 수 × 박 간격 − 출력 지연.
3. 1마디 전: 다시 확인한다. 실패하면 예약을 취소하고 "직접"을 띄운다.
4. 예약 시각: 지금 보이는 쪽이 그 넘김의 "넘기기 전 쪽"일 때만 넘긴다. 손으로 이미 넘겼으면 건너뛴다.
5. 손으로 넘기면 바로 따른다. 자동 넘김은 보이는 쪽과 엔진 위치가 다시 맞는 다음 넘김부터 한다.
6. 파트 준비 때 "직접"으로 정한 넘김은 자동으로 하지 않는다.

### 6.3 넘김표

- 넘김은 (원곡 박 번호, 넘긴 뒤 보일 쪽) 목록이다. 원곡은 반복이 펼쳐진 연주 순서라서 박 번호는 항상 늘어난다. 반복 때문에 앞 쪽으로 가는 넘김도 같은 목록에 들어간다.
- 어떤 박에서 보일 쪽 = 그 박 전의 마지막 넘김이 가리키는 쪽 (없으면 첫 쪽). 재시작으로 위치가 바뀌면 이 규칙으로 쪽을 다시 정한다.
- 반복되는 쪽(같은 쪽이 두 번 보임)은 "펼친 쪽" 재시작에서 후보 범위가 둘 이상이 된다. 구간 버튼으로 구별한다.

### 6.4 오류 처리

| 상황 | 앱의 동작 |
|---|---|
| 마이크 권한 거부 | 연주 화면에서 손 넘김만 된다. 권한 안내 |
| 다른 앱이 마이크를 씀 (전화 등), 입력 끊김 | "듣기 끊김" 표시, 자동 넘김 정지, 입력을 다시 연다 |
| 입력 찌그러짐 | 상태 줄에 경고. 기록에 남긴다 |
| 말소리 처리를 끄는 입력 모드가 없는 기기 | 대체 모드로 열고 설정에 표시한다 (11절) |
| PDF를 못 엶 (암호, 손상) | 넣기 단계에서 알린다 |
| 원곡 파일을 못 읽음 (보호된 파일 등) | 곡 준비 단계에서 알린다. 마이크로 듣기를 안내한다 (F17이 생긴 뒤) |
| 곡 패키지 버전이 엔진과 다름 | 다시 분석하라고 알린다 (원곡 파일 필요) |
| 처리가 밀림 (분석이 실시간을 못 따라감) | 자동 넘김을 멈추고 "직접". 기록에 남긴다 |

## 7. 구조

### 7.1 네이티브여야 하는 부분

| 부분 | 네이티브 | 이유 |
|---|---|---|
| 마이크 입력 | 필요 | OS의 말소리 처리(자동 음량 조절, 잡음 제거)를 끄는 입력 모드로 열어야 한다 (R8). 오디오 스레드에서 끊김 없이 받아야 한다 |
| 분석 엔진 | 필요 (C++) | 짧고 일정한 지연. 메모리 정리(GC)로 멈추면 안 된다. 안드로이드·iOS·맥이 같은 코드를 쓴다 |
| 넘김 시각 실행 | 필요 | 화면 갱신 주기에 맞춰 정한 시각에 쪽을 바꾼다 |
| PDF 그리기 | OS 기능 | 안드로이드 PdfRenderer, iOS PDFKit |
| 음원 파일 읽기 | OS 기능 | 안드로이드 MediaExtractor + MediaCodec, iOS AVAudioFile |
| 화면 | 선택 | 7.2절 |

### 7.2 화면 기술 [제안]

- **안드로이드는 Kotlin + Jetpack Compose로 만들고, 엔진은 JNI로 붙인다.**
- 화면을 한 벌로 만드는 도구(Flutter 등)를 쓰지 않는 이유: 마이크, 엔진, 정한 시각의 넘김, PDF, 음원 읽기가 모두 결국 네이티브 코드다. 화면은 다섯 개로 작다. 두 층을 잇는 비용이 화면 한 벌을 아끼는 것보다 크다고 본다 [추정].
- 아이패드·아이폰·맥 화면은 안드로이드가 자리 잡은 뒤 정한다 (SwiftUI로 따로 만들거나, Kotlin Multiplatform으로 화면을 나눠 쓰거나). 멤버 기기 중 아이패드가 많으면 앞당긴다.
- 그때 옮기기 쉽게, 곡·넘김표·상태 처리 코드는 안드로이드 기능을 쓰지 않는 순수 Kotlin 모듈로 둔다.

### 7.3 계층

```
화면 (Kotlin, Compose)
  곡 목록 · 곡 준비 · 파트 준비 · 연주 · 설정
앱 처리 (순수 Kotlin)
  곡·파트·넘김표 저장 · 셋리스트 · 상태 표시 규칙 · 기록 관리
기기 계층 (Kotlin + C++)
  마이크(Oboe) · 원곡 재생 · 음원 읽기(MediaCodec) · PDF(PdfRenderer) · 시계(Choreographer)
엔진 (C++, 모든 기기 공통)
  실시간: 온셋 → 박 추적 → 연주 시작·멈춤 → 크로마 → 박 단위 정렬 → 넘김 예약
  오프라인: 원곡 분석 (템포, 박 격자, 마디 첫 박, 드럼 줄이기, 박 단위 크로마)
```

### 7.4 스레드와 시계 [제안]

| 스레드 | 하는 일 | 규칙 |
|---|---|---|
| 오디오 (Oboe 콜백) | 마이크 샘플을 링 버퍼에 복사 | 메모리 할당, 잠금, 대기 금지 (기획 2.5절) |
| 분석 | 링 버퍼에서 꺼내 22,050 Hz로 바꾸고 엔진을 돌린다. 박마다 사건을 큐에 넣는다 | 우선순위를 높인다 |
| 화면 (메인) | 화면 갱신마다 사건 큐를 읽고 표시. 예약 시각에 쪽을 바꾼다 | 바꿀 쪽은 미리 그려 둔다 |
| PDF 그리기 | 현재 쪽, 다음 넘김의 쪽, 이전 쪽을 그려 둔다 | PdfRenderer는 한 번에 한 쪽만 연다 |
| 기록 | 소리를 AAC로 저장, 사건 기록 | 오디오 스레드와 분리 |

**시계 맞추기**
- 입력 쪽: 마이크 샘플 번호와 기기 시계(CLOCK_MONOTONIC)를 AAudio의 getTimestamp로 잇는다 [확인 필요: 입력 스트림에서 값이 나오는지, S23 울트라에서]. 안 되면 콜백 도착 시각과 입력 지연 추정값으로 잇는다.
- 출력 쪽: 안드로이드 13(API 33) 이상은 화면 갱신마다 "이 프레임이 화면에 보일 예상 시각"을 OS가 준다 (Choreographer VsyncCallback의 FrameTimeline). 그 시각이 넘김 목표 시각에 가장 가까운 프레임에서 쪽을 바꾼다. 출력 지연을 따로 잴 필요가 거의 없다 [확인 필요: 실제 오차].
- 두 시계는 같은 기준(System.nanoTime)이다. 넘김 시각은 이 기준으로 계산한다.
- 허용 오차가 ±1박(♩=160에서도 0.38초)이라, 시계 맞추기 오차가 수십 ms면 충분하다 [추정].

**입력 설정**
- 입력 모드: Unprocessed(말소리 처리 없음, 기기가 지원할 때) → 안 되면 VoiceRecognition.
- 성능 모드 LowLatency, 공유 모드 Shared, 모노, 32비트 실수, 기기 기본 표본율(보통 48 kHz).
- 블루투스 이어폰이 연결돼 있어도 내장 마이크를 고른다.

**표본율**
- 엔진은 Python과 같은 22,050 Hz에서 돈다. 48 kHz → 22,050 Hz 변환을 엔진에 넣는다.
- 24 kHz(48 kHz의 절반)로 바꾸면 변환이 단순해지지만 설정값을 다시 검증해야 해서 처음에는 하지 않는다.

### 7.7 저작권·개인정보 원칙 (기획 4.9절 P14 적용)

1. 앱은 음악을 제공하지 않는다. 사용자가 가진 원곡 파일을 기기 안에서 분석한다.
2. 원곡 소리를 저장하거나 보내지 않는다. 곡 패키지에는 분석 결과만 있다.

4. 합주 녹음(기록)은 기기 안에만 있고, 사용자가 직접 내보낼 때만 밖으로 나간다.
5. 공개 배포 전 법률 검토를 받는다 (기획 그대로).

## 15. M2: 기록 모드와 첫 합주 (v1.1) [확정: M2 먼저. 상세는 제안]

### 15.1 합주 녹음이 필요한 이유

- **완성된 앱에는 합주 녹음이 필요 없다.** 앱은 원곡만으로 첫 합주부터 동작한다 (U14). 녹음은 개발과 시험에만 쓴다. 기록 모드는 기본으로 꺼 둔다.
- 앱이 실제로 들을 소리는 "합주실 보면대 위의 폰이 말소리 처리 없이 듣는 소리"다. 지금까지의 시험은 녹음 조건을 모르는 파일과 흉내(휴대폰 대역, 자동 음량 조절, 잘라 붙인 재시작, 드럼 지우기)로 했다. 이 조건으로는 한 번도 재 보지 않았다 (R8).
- 기존 녹음 7개로 안 되는 것:

| 필요한 것 | 기존 7개 | 기록 모드 |
|---|---|---|
| 앱과 같은 입력 설정 (말소리 처리 끔) | 삼성 음성 녹음 앱. 처리를 걸었는지 모른다 | 같다 |
| 폰 위치 | 모른다 | 보면대 (사진 한 장) |
| 사람이 넘긴 시각 | 없다 | 소리와 같은 시계로 남는다 |
| 실제 재시작, 드럼이 쉬는 대목 | 들어 있을 수 있지만 표시가 없다 | 곡 선택과 넘김 기록으로 찾기 쉽다 |
| 폰 화면 크기, 발열, 배터리 | 해당 없음 | 확인한다 |

- 한 번 녹음해 두면 엔진을 고칠 때마다 같은 합주를 다시 흘려 넣어 시험할 수 있다. 시험하려고 합주를 다시 할 필요가 없다.
- 위치 정확도까지 재려면 그 곡의 원곡이 있어야 한다. 원곡이 없는 곡은 실제 소리 조건(음량, 찌그러짐, 박 추적, 연주 시작·멈춤 감지)만 본다.

### 15.2 M2에 들어가는 것

| 부분 | 내용 |
|---|---|
| 악보 목록 | PDF 넣기 (시스템 파일 선택기). 곡 이름은 파일 이름 (바꿀 수 있다) |
| 악보 화면 | 전체 화면, 왼쪽·오른쪽 탭으로 넘김, 쪽 번호, 화면 꺼짐 방지, 방향 고정, 여백 자르기 켜기·끄기 |
| 기록 | [기록 시작]·[기록 끝]. 기록 중 곡을 바꾸면 새 파일로 나눈다 |
| 입력 확인 | 음량 막대, 찌그러짐 횟수, 실제로 열린 입력 모드 (Unprocessed 또는 대체 모드) |

저장 내용 (곡마다 한 묶음)

| 파일 | 내용 |
|---|---|
| 소리 | AAC 48 kHz 모노 128 kbps. 앱이 갑자기 꺼져도 앞부분이 남는 형식(ADTS)으로 쓴다 |
| 사건 기록 | 쪽 넘김(시각, 몇 쪽 → 몇 쪽), 곡 선택, 기록 시작·끝, 앱 벗어남·복귀, 매초 음량·찌그러짐, 매분 배터리·온도 |
| 정보 | 기기, 안드로이드 버전, 입력 모드, 표본율, 시작 시각, 앱 버전 |

- 쪽 넘김 시각은 소리의 몇 번째 샘플인지로도 적는다 (7.4절 시계 맞추기).
- 앱을 벗어나면 기록을 멈추고 파일을 닫는다. 돌아오면 새 파일로 이어서 기록한다 (11절: 백그라운드를 쓰지 않음). 합주 중에 이 때문에 자료를 잃으면 그때 백그라운드 기록을 검토한다.
- 기록은 폰의 "내 파일" 앱에서도 보이는 곳에 저장한다. 맥으로는 USB 연결 뒤 내가 가져온다 (adb).
- 엔진, 자동 넘김, 원곡 분석은 넣지 않는다 (M3 이후).

### 15.3 M2가 끝나는 조건

1. 집에서 10분 이상 녹음하며 쪽을 넘겨 봤을 때, 소리와 넘김 시각이 맞는다 (넘길 때 손뼉을 쳐서 확인).
2. 앱을 잠깐 벗어났다 돌아와도 파일이 깨지지 않는다.
3. 합주 한 번(2~3시간)의 기록이 끊김 없이 남는다 (실제 합주에서 확인).

### 15.4 합주 전 (사용자)

1. 폰에서 개발자 옵션과 USB 디버깅을 켜고 맥에 연결해 앱을 설치한다. 한 번만 하면 되고, 그때 같이 한다.
2. 칠 곡의 자기 파트 PDF를 앱에 넣는다. PDF가 없는 곡도 녹음은 된다 (넘김 시각만 없다).
3. 원곡을 구할 수 있는 곡이 한 곡이라도 있으면 그 곡을 꼭 친다. 위치 정확도까지 잴 수 있다 (띵바츄는 원곡이 이미 있다).
4. 폰을 충전하고 방해 금지 모드를 켠다.

### 15.5 합주 중 (사용자)

1. 폰을 평소 악보를 보는 자리(보면대)에 둔다. 폰 자리와 드럼이 함께 나오게 사진을 한 장 찍는다.
2. 합주를 시작할 때 [기록 시작]을 누른다. 곡을 칠 때마다 그 곡 악보를 연다.
3. 평소처럼 연주하고 쪽은 화면을 탭해서 넘긴다. 멈추고 다시 치기, 잡담, 튜닝은 모두 그대로 둔다. 따로 할 일은 없다.
4. 다른 멤버는 아무것도 하지 않아도 된다.
5. 악보가 이 폰에서 읽히는지, 화면이 꺼지거나 폰이 뜨거워지는지만 기억해 둔다.

### 15.6 합주 뒤

1. 폰을 맥에 연결한다. 기록을 가져와 분석한다 (Claude).
2. 보는 것: 입력 음량과 찌그러짐, 실제 소리에서의 박 추적과 연주 시작·멈춤 감지, 사람이 넘긴 시각이 페이지 끝보다 얼마나 이른지, 배터리·발열.
3. 원곡이 있는 곡은 Phase 1-b와 같은 방식으로 정답을 만들고 넘김 예측을 잰다 (엔진 이식 전이라도 Python으로 할 수 있다).

### 15.7 합주 전에 앱이 준비되지 못하면

- 삼성 음성 녹음 앱으로 보면대 자리에서 녹음한다. 쪽을 넘길 때마다 녹음 앱의 북마크를 누르면 넘김 시각이 남는다. 입력 설정은 앱과 다르다.

## 16. 플랫폼 재검토: 설치 없는 웹앱 (v1.2) [철회 (v1.3), 16.7절]

### 16.1 계기 (기획 U17)

- 사용자: "악보 보는 사람들은 아이패드 사용자가 많은데 아이패드에 앱을 설치하는 게 되게 귀찮은데", "휴대전화로 악보를 보지는 않지 보통."
- 그래서 주 기기는 아이패드(태블릿)다. 휴대폰(S23 울트라)은 악보 기기가 아니라 녹음 기기로만 쓴다. 11절의 "첫 시험 기기 S23 울트라"와 "폰 화면 크기" 걱정은 해당이 없어진다.

### 16.2 아이패드 네이티브 앱의 설치 부담 (2026-11-19 확인)

| 대상 | 방법 | 부담 |
|---|---|---|
| 본인 아이패드 | 이 맥의 Xcode(26.6, iOS SDK 26.5 설치됨)로 무료 계정 설치 | 7일마다 맥에 연결해 다시 설치해야 한다 |
| 멤버 아이패드 | 유료 개발자 계정(연 99달러) + TestFlight 초대, 또는 App Store 심사 | 계정 비용. 멤버마다 TestFlight 앱 설치와 초대 수락. 시험판은 90일마다 새로 올려야 한다 |

### 16.3 제안: 웹앱

- 링크를 사파리로 열면 된다. 설치가 없다. "홈 화면에 추가"를 하면 주소창 없는 전체 화면으로 앱처럼 쓴다.
- 아이패드(사파리), 안드로이드 태블릿(크롬), 맥북(사파리·크롬)을 한 코드로 지원한다 (U13의 세 기기).
- 고치면 다음에 열 때 바로 반영된다. 멤버에게 다시 설치해 달라고 할 일이 없다.
- 기획 4.6절에서 웹을 뺀 이유는 "마스터 노트북이 합주실 LAN에서 페이지를 띄우는 구조"의 보안 연결 문제였다 (HTTP면 화면 꺼짐 방지 불가, HTTPS면 LAN 접속 차단). 기기마다 각자 듣는 구조(D2)에서는 페이지를 인터넷의 HTTPS로 받고 LAN 접속이 없으므로 그 문제가 없다.
- 홈 화면 웹앱에서 화면 꺼짐 방지가 안 되던 버그는 iPadOS 18.4에서 고쳐졌다 [확인 필요: 멤버 아이패드 버전].
- 녹음(마이크 입력)은 브라우저에서도 된다. 남는 질문은 "말소리 처리를 끈 소리를 받을 수 있는가"다 (16.5절).

|---|---|---|
| W-1 | 말소리 처리를 끈 마이크 소리를 주는가 (끄는 설정이 실제로 적용되는지, 음량이 저절로 바뀌는지) | R8. 웹의 가장 큰 불확실성이다. 아이패드 사파리는 에코 제거를 끄면 말소리 처리 없는 입력으로 바뀌는 것으로 알고 있다 [확인 필요] |
| W-2 | 합주 음량에서 입력이 찌그러지는가 | 내장 마이크 한계 |
| W-3 | 화면 꺼짐 방지가 2~3시간 유지되는가, 마이크 권한을 매번 묻는가 | 사용성 |
| W-4 | 다른 앱을 갔다 오거나 알림이 와도 마이크가 다시 열리는가 | 오류 처리 (6.4절) |
| W-5 | 저장한 악보와 기록이 며칠 뒤에도 남는가 (홈 화면 추가, 저장 유지 요청) | 사파리는 오래 안 쓴 사이트의 저장소를 지울 수 있다 |

- 방법: 마이크 시험 페이지 한 장 (음량 막대, 실제 적용된 입력 설정 표시, 30초 녹음·재생·내보내기). 아이패드에서 10분이면 된다. 시험할 아이패드(본인 또는 멤버)가 필요하다.
- 시험 페이지는 HTTPS로 열어야 한다 (브라우저 마이크 조건). 가장 빠른 방법은 claude.ai의 비공개 Artifact 페이지다 (로그인한 기기에서 열림) [확인 필요: 마이크 권한]. 아니면 무료 정적 호스팅에 올린다.
- W-1이 안 되면: 아이패드에서는 웹 화면을 네이티브 앱 안에 넣고 마이크만 네이티브로 받는다 (WKWebView, Capacitor 등). 엔진과 화면 코드는 그대로 쓴다. 이때는 16.2절의 설치 부담이 다시 생긴다.

### 16.6 바뀐 순서 (웹앱으로 정하면)

| 단계 | 내용 | 기기 |
|---|---|---|
| W0 | 마이크 시험 페이지 (16.5절) | 아이패드, S23 울트라 |
| M2 | 웹 기록 모드: 악보 보기, 탭 넘김, 보면대 녹음, 넘김 시각 기록 (15절 내용 그대로, 기기만 아이패드) | 아이패드 (안드로이드 태블릿과 폰에서도 동작) |
| M1 | 엔진 이식 (TypeScript) + Python과 결과 비교 | 맥 (Node 20 설치됨) |
| M3~ | 10절과 같다 (예측 모드 → 자동 넘김 → 앱 안 곡 준비 → 멤버 배포) | 아이패드 |

- 안드로이드 빌드가 없으므로 디스크 정리는 급하지 않다. 웹 개발 도구는 수백 MB다. 재부팅(스왑 정리)은 권한다.
- 합주 기록(15절)도 아이패드에서 한다. S23 울트라는 같은 웹앱으로 열어 녹음 비교용으로 쓸 수 있다.

### 16.7 재검토 2: 웹 철회, 네이티브 유지, 아이패드 먼저 (v1.3) [제안, 사용자 결정 대기]

**계기 (기획 U18, 2026-11-20)**: 사용자 "이거 계산기같이 인터넷이 필요 없는 앱인데 웹으로 배포해서 할 필요가 있을까? 반응성이 중요한 앱인데?"

**판단**

- 웹을 제안한 이유는 시험 단계의 아이패드 설치 부담 하나였다. 앱이 동작하는 데 인터넷은 필요 없다. 웹은 설치 편의를 얻는 대신 아래 세 가지를 브라우저에 맡기는 선택이었다.
- 넘김 동작 자체의 속도는 웹도 문제가 아니다. 넘김은 1~2마디 앞에서 계산하고(기획 4.7절) 다음 페이지는 미리 그려 두므로, 넘기는 순간에는 화면 갱신 한 번(8~17 ms)이면 된다. 허용 오차는 ±1박이다 (시범곡 ♩=85에서 0.71초, ♩=180이어도 0.33초).
- 이 앱의 핵심 세 가지는 네이티브라야 확실하다.

| 부분 | 웹 (사파리) | 네이티브 (iPadOS) |
|---|---|---|
| 마이크 | 말소리 처리를 끄라고 요청만 한다. 실제 적용은 브라우저가 정한다 (16.5절 W-1) | AVAudioSession의 measurement 모드로 시스템 신호 처리를 최소로 한다 |
| 시각 | 마이크 입력 지연을 정확히 알기 어렵다 [확인 필요]. 메모리 정리로 잠깐 멈출 수 있다 [추정] | 입력 버퍼마다 호스트 시각(AVAudioTime)이 붙고 입력 지연 값(inputLatency)을 읽을 수 있다. 화면은 CADisplayLink가 다음 표시 시각을 준다 |
| 저장 | 사파리가 저장소를 지울 수 있다 (16.5절 W-5) | 앱을 지우기 전까지 남는다 |

- 그래서 웹 제안은 철회한다. 7절 구조(C++ 엔진 공통 + 기기별 네이티브 화면)를 그대로 쓴다.

**제안: 아이패드 먼저**

- 악보는 아이패드로 본다 (U17). M2 기록 모드는 악보를 보면서 탭으로 넘기고 그 시각을 적는 것이라, 악보를 보는 기기에서 돌아야 한다. 휴대폰(S23 울트라)에서 하면 실제 사용과 다르다.
- 화면은 Swift + SwiftUI로 만든다. 엔진은 7.5절 C++ 그대로 쓰고 Swift에서 C API로 부른다.
- 같은 앱이 아이폰과 애플 실리콘 맥에서도 돈다. U13의 맥북은 이것으로 지원할 수 있다 [확인 필요: 맥에서 마이크 입력 품질].
- 안드로이드(태블릿)는 같은 엔진에 Kotlin 화면을 붙여 나중에 만든다. 11절은 그때 쓴다.
- M2에는 엔진이 필요 없다 (15.2절). M2는 Swift만으로 만든다.

**아이패드 세부 [제안]** (11절과 짝)

| 부분 | 아이패드 |
|---|---|
| 마이크 | AVAudioSession 카테고리 record, 모드 measurement. measurement 모드는 주 마이크 하나만 쓴다. 48 kHz 모노로 받아 엔진에서 22,050 Hz로 바꾼다 |
| 입력 시각 | 입력 버퍼의 AVAudioTime 호스트 시각 + AVAudioSession.inputLatency |
| 넘김 시각 | CADisplayLink targetTimestamp (7.4절 Choreographer 자리) |
| PDF | PDFKit. 다음 페이지를 미리 그려 둔다 |
| 악보 가져오기 | 파일 앱에서 고르고(fileImporter) 앱 저장소에 복사한다 |
| 기록 꺼내기 | 앱 폴더를 파일 앱에 보이게 한다 (UIFileSharingEnabled, LSSupportsOpeningDocumentsInPlace). 맥으로는 AirDrop 또는 USB 연결 뒤 Finder로 옮긴다. 15.6절의 방법을 대신한다 |
| 화면 켜 두기 | isIdleTimerDisabled |
| 녹음 파일 | 15.2절과 같다 (ADTS AAC) [확인 필요: iPadOS에서 ADTS로 기록] |
| 권한 | 마이크 하나 (NSMicrophoneUsageDescription). 백그라운드 실행 없음 |
| 최소 iPadOS | 합주에 쓸 아이패드의 버전을 보고 정한다 [확인 필요] |

**환경 (2026-11-20 확인)**

- 이 맥은 애플 실리콘(Apple M2 Pro 칩)이다.
- 이 맥에 연결된 적 있는 iOS 기기는 아이폰뿐이고 아이패드는 없다.
- iOS 서명 인증서(개발용·배포용)가 이미 있다. 개인 프로젝트에 어느 Apple 계정을 쓸지는 사용자가 정한다.
- 디스크 여유 4.9 GB (11/19에는 2.2 GB, 스왑에 따라 바뀜). 기기를 처음 연결하면 Xcode가 디버깅용 기기 파일을 받아 수 GB가 더 들 수 있다 [추정]. 안드로이드 에뮬레이터 이미지·AVD·에뮬레이터(약 12 GB, 12절)는 실기기로 시험하면 필요 없다. 삭제는 사용자가 고른 것만 한다.
